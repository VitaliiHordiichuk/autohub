# Автоматическая очистка истории

## Однократное включение при выпуске

1. Сделать штатную резервную копию production PostgreSQL и проверить возможность восстановления.
2. Применить **только** `migrations/077_add_automatic_data_retention.sql` обычным способом от роли владельца схемы. Эта миграция сама ничего не удаляет: добавляет индексы, контрольную запись обслуживания и независимый признак успешного почтового импорта. Повторный запуск безопасен.
3. При желании до запуска нового backend выполнить `npm run report:data-retention`: это строго read-only отчёт с числом кандидатов и последним результатом обслуживания.
4. Перезапустить обновлённый backend. `DATA_RETENTION_ENABLED=true` используется по умолчанию. После старта первый запуск происходит через минуту. Frontend можно обновить следом — он показывает сроки хранения.

После выпуска ручное обслуживание истории не требуется. Планировщик проверяет состояние раз в час, выполняет полную очистку раз в 24 часа, продолжает частичный проход через минуту и повторяет неудачный через 5 минут. Контрольная запись хранится в БД и переживает перезапуски. Несколько процессов backend защищены общей PostgreSQL advisory lock. Для аварийной остановки установить `DATA_RETENTION_ENABLED=false` и перезапустить backend.

Если миграция не применена, очистка **ничего не удаляет**, пишет ошибку и ожидает готовности схемы. Не следует выкатывать новый почтовый импорт без миграции 077.

## Политика

| Данные | Срок / условие |
|---|---|
| `imports`, `import_rows`, исходные строки и ошибки отчётов | Последние 5 терминальных попыток (`COMPLETED`, `COMPLETED_WITH_ERRORS`, `FAILED`) на пару склад + профиль импорта. Старые записи без профиля образуют отдельную группу на склад. Текущие обработки не считаются в пятёрку. |
| `search_events` + дочерние `search_event_results` | 30 дней; это также история поисков в кабинете клиента. |
| `price_history` | 90 дней; текущие цены и сравнение при следующем импорте читаются из предложения, не из истории. |
| `user_notifications` | 30 дней после прочтения, 90 дней после создания для непрочитанных. |
| `customer_history` | `LOGIN` — 30 дней; четыре события восстановления/смены пароля — 90 дней. Изменения скидок/номеров клиента и другие типы не очищаются. |
| `password_reset_requests` | 90 дней, без нарушения актуального окна ограничения запросов. |
| `password_reset_tokens`, `telegram_link_tokens` | 7 дней после истечения; использованные reset-токены — 7 дней после использования. |
| `checkout_sessions` | Незавершённые/отменённые/истёкшие оформления с истёкшим более 30 дней назад сроком и без свежих обновлений или защищённых резервов. `COMPLETED` не удаляется. |
| `stock_reservations` | Только истёкшие более 30 дней назад `ACTIVE`/`RELEASED`/`CANCELLED`, без заказа; бессрочные и неизвестные статусы защищены. |
| `carts` + их состав | Только гостевые без активности 30 дней, без завершённого оформления, свежих позиций/оформлений или защищённых резервов. Корзины зарегистрированных пользователей сохраняются. |

## Гарантии и ограничения

- Только разрешённый список таблиц. Не удаляются товары, предложения, остатки, цены, ручные исправления, пользователи, заказы, возвраты, VIN-переписка, складские движения, история изменений заказов, переводы и решения очереди проверки новых товаров (в том числе отказы).
- Удаление старого отчёта отвязывает `import_new_products` от отчёта, но не удаляет саму очередь/решение. Свежие отчёты, отчёты младше часа и потоки с выполняющимся импортом защищены. Поэтому временно возможно больше пяти отчётов.
- Служебные идентификаторы обработанных email-вложений и курсор почтового ящика сохраняются: это защита от повторного применения старого прайса, а не пользовательская история файлов. Через 90 дней у завершённых вложений без отчёта стираются имя файла, отправитель, тема и текст ошибки; остаются служебные ключи. Признак `has_successful_import` переживает удаление отчёта; неуспешные импорты не становятся успешными дубликатами. При одновременной очистке и обнаружении дубликата вставка новой служебной ссылки не требует уже удалённого отчёта.
- Аутентифицированный доступ к гостевой корзине обновляет её время активности максимум раз в час, чтобы используемая корзина не считалась брошенной.
- Удаление идёт пакетами до 500 родительских записей; строки больших импортов очищаются отдельно такими же пакетами. Каскадные дочерние строки также удаляются. Транзакции имеют `lock_timeout=2s`, `statement_timeout=15s`. На запуск выделено около 30 секунд; начальная большая очистка может занять несколько проходов с минутными перерывами. Заблокированные записи пропускаются и будут обработаны следующим проходом.
- `data_retention_state` содержит одну перезаписываемую запись: статус, последний результат, время успешного прохода и ошибку. Это не новая растущая история очисток. Счётчики удаления родительских таблиц не включают неявные каскадные удаления.
- Физический размер PostgreSQL может не уменьшиться сразу после DELETE. Должен быть включён штатный **autovacuum**, который освобождает место для повторного использования. `VACUUM FULL` автоматически не запускается: он блокирует таблицы. Очистка ограничивает ненужную историю, но не запрещает рост полезных товаров и заказов.
- Эта задача не удаляет резервные копии, серверные логи, почту или изображения в R2. Для них нужны отдельные правила на стороне соответствующего хранилища.

## Проверка

`npm test` создаёт отдельную базу с суффиксом `_test`, применяет миграции и запускает unit/API/integration suite. Тесты очистки проверяют реальное удаление, dry-run, повторный запуск, частичный проход, защиту активных импортов/корзин, сохранение очереди и действующих цен, независимую почтовую дедупликацию и межпроцессную блокировку. Рабочая БД не изменяется.

После выкладки: `npm run report:data-retention` показывает `state.status`, `last_completed_at` и оставшихся кандидатов. При `PARTIAL` работа продолжается автоматически, при `FAILED` сохраняется причина и выполняется повторная попытка. Не удалять `PROCESSING` вручную только из-за возраста: сначала проверить, действительно ли обработка остановилась.
